## 1. ทีมขออะไร

1. มีปุ่มให้ผู้รับบริการกด **ออก QR ใหม่** (token เดิมต้องใช้ไม่ได้ทันที)
2. token ตอน **เช็คอิน** กับ **เช็คเอาท์** ต้องเป็น **คนละค่ากัน**

ทั้งสองข้อขัดกับสิ่งที่ PYG-434 ตั้งใจไว้ตอนแรก ซึ่งเขียนไว้ในโค้ดตรง ๆ ว่า
เลือก "QR ใบเดียวต่อ booking ไม่มีวันเปลี่ยน" เพื่อให้ **ปริ้นท์แปะตู้เย็นได้**
และปฏิเสธแนวคิด rotate ไปแล้ว

**ทีมรับข้อแลกเปลี่ยนแล้ว:**

| | |
|---|---|
| ✗ เสียไป | ปริ้นท์ QR แปะไว้ล่วงหน้าไม่ได้อีก — ใบที่ปริ้นท์ตายทันทีที่เช็คอินสำเร็จ |
| ✓ ได้มา | QR หลุด (ถูกถ่ายรูป/ส่งต่อในแชต) → ผู้รับบริการกดออกใหม่เองได้ ไม่ต้องรอแอดมิน |
| ✓ ได้มา | ใครถือ QR ตอนเริ่มงานไว้ เอาไปกดปิดงานเองไม่ได้ |
| ✓ ได้มา | "สแกนรัวสองครั้งแล้วงานเปิด-ปิดใน 1 วินาที" หมดไปที่ระดับโครงสร้าง — เดิมกันด้วย `QR_MIN_SECONDS_BETWEEN_ACTIONS` ซึ่งเป็นแค่การหน่วงเวลา |

## 2. ทำไมถึงไม่ต้อง migrate

### 2.1 สูตร token เปลี่ยน แต่ที่เก็บไม่เปลี่ยน

```
เดิม (v1)  token = HMAC(secret, "payung:jobqr:v1:<session id>")
ใหม่ (v2)  token = HMAC(secret, "payung:jobqr:v2:<session id>:<action>:<updated_at ms>")
```

ทั้งสองสูตรให้ผลเป็น **base64url 43 ตัว** เหมือนเดิม
และดีบียังเก็บ **`token_hash` ค่าเดียวต่อแถว** เหมือนเดิมทุกประการ

`token_hash` = sha256 ของ token ที่ใช้ได้ **"ตอนนี้"**
→ ไม่ต้องเพิ่มคอลัมน์ ไม่ต้องเพิ่ม index ไม่ต้องแก้ตรรกะการค้นหาของ `scanJobQr`

### 2.2 "เลขรอบ" ใช้ `updated_at` ที่มีอยู่แล้ว

สิ่งที่ทำให้ token เปลี่ยนได้ คือการมีตัวเลขสักตัวในสูตรที่ขยับได้
ทางที่สะอาดที่สุดคือเพิ่มคอลัมน์ `token_version INTEGER` — **แต่นั่นต้อง migrate**

`updated_at` ทำหน้าที่แทนได้ครบ เพราะมันคือ "แถวนี้ถูกแก้ล่าสุดเมื่อไหร่":

| เหตุการณ์ | `updated_at` ขยับไหม | token เปลี่ยนไหม |
|---|---|---|
| กดปุ่ม "ออก QR ใหม่" | ✓ | ✓ |
| สแกนเช็คอินสำเร็จ | ✓ | ✓ (กลายเป็น token ของ CHECK_OUT) |
| สแกนเช็คเอาท์สำเร็จ | ✓ | — (ตั้งใจไม่เปลี่ยน ดูหัวข้อ 5) |
| อ่าน QR เฉย ๆ | ✗ | ✗ |

และเพราะเวลาเดินหน้าทางเดียว → **token เก่าที่เคยหลุดไปแล้ว ไม่มีวันกลับมาใช้ได้อีก**

### 2.3 แถวเก่าซ่อมตัวเอง — จึงไม่ต้องมี backfill script

`token_hash` ที่อยู่ในดีบีตอนนี้ทั้งหมดคำนวณด้วยสูตร v1
ซึ่งไม่มีทางตรงกับ v2 → ปกติจะต้องเขียนสคริปต์ไล่เขียนใหม่ทุกแถว
(เขียนด้วย SQL ล้วนไม่ได้ เพราะ Postgres ไม่รู้จัก `QR_TOKEN_SECRET`)

**แต่ `JobQrService.syncTokenHash()` จัดการให้แล้ว:** ทุกครั้งที่ผู้รับบริการเปิดหน้า QR
ระบบจะเทียบว่า `token_hash` ในดีบีตรงกับสูตรปัจจุบันไหม ถ้าไม่ตรงก็เขียนให้ตรงเสียเลย

- เขียนแบบมีเงื่อนไข (compare-and-swap) → ไม่ทับของใหม่ที่คนอื่นเพิ่งเขียน
- เขียน **ครั้งเดียวต่อแถว** แล้วเงียบไปตลอด (มีเทสคุมว่าแถวที่ถูกต้องแล้วต้องไม่เขียนซ้ำ)
- ครอบคลุมกรณี `QR_TOKEN_SECRET` ถูกเปลี่ยนด้วย ซึ่งเดิมต้องเขียนสคริปต์เหมือนกัน

## 3. สิ่งที่ **ต้อง** ทำก่อน deploy production

**ไม่มีงานดีบี** แต่มีข้อเดียวที่ต้องยืนยัน:

### ⚠ `QR_TOKEN_SECRET` ต้องมีค่าจริงและ **ห้ามเปลี่ยน**

| สภาพแวดล้อม | ไม่ตั้งค่า → เกิดอะไร |
|---|---|
| production | แอป **ไม่ยอมบูต** (ตั้งใจให้พังเสียงดัง) |
| dev / test | สุ่มกุญแจใหม่ทุกครั้งที่ restart → QR เปลี่ยนเงียบ ๆ |

**สถานะตอนนี้:** `.env` ของเครื่อง dev **ยังไม่ได้ตั้งค่านี้**
ผลคือทุกครั้งที่ restart backend ระหว่างทดสอบ token จะเปลี่ยนทั้งระบบ
(`syncTokenHash()` ซ่อมให้ตอนเปิดหน้า จึงยังทดสอบต่อได้ แต่ QR ที่แคปหน้าจอไว้จะใช้ไม่ได้)

ถ้าเจอ `TOKEN_NOT_FOUND` แบบไม่มีเหตุผลระหว่างทดสอบ ให้สงสัยข้อนี้เป็นข้อแรก
คัดลอกค่าจาก `.env.example` ไปตั้งใน `.env` แล้วอาการจะหาย

## 4. หลัง deploy จะเกิดอะไรขึ้นกับข้อมูลที่มีอยู่

| สถานการณ์ | ผลลัพธ์ |
|---|---|
| booking ที่ยังไม่เช็คอิน | ผู้รับบริการเปิดหน้า → ได้ QR ใบใหม่ทันที · ใบเก่าที่แคปไว้ใช้ไม่ได้ |
| booking ที่เช็คอินแล้ว รอเช็คเอาท์ | ได้ QR ของ "จบงาน" ซึ่งเป็นคนละใบกับตอนเริ่มงาน |
| booking ที่ปิดงานแล้ว | ไม่มีอะไรเปลี่ยน · สแกนซ้ำยังได้ข้อความ "งานนี้ปิดเรียบร้อยแล้ว" เหมือนเดิม |
| booking ก่อน migration `20260828000000` | ไม่มีแถวใน `job_sessions` อยู่แล้ว → ยังใช้ QR ไม่ได้เหมือนเดิม (ไม่ใช่เรื่องของ PR นี้) |

**ช่วงเปลี่ยนผ่านที่ต้องระวัง:** ผู้ดูแลที่แคปหน้าจอ QR ไว้ก่อน deploy จะสแกนไม่ผ่าน
และได้ข้อความ *"QR นี้ใช้ไม่ได้ กรุณาให้ผู้รับบริการเปิด QR จากแอปอีกครั้ง"*
ซึ่งบอกวิธีแก้ไว้ในตัวแล้ว — ให้ผู้รับบริการเปิดหน้าใหม่ก็จบ

**ไม่ต้อง rollback** ถ้าเจออาการนี้ มันคือพฤติกรรมที่ตั้งใจ

## 5. การตัดสินใจที่ควรรู้ตอนรีวิว

### 5.1 เช็คเอาท์สำเร็จแล้ว "ไม่" เปลี่ยน token

ถ้าเปลี่ยน จะไม่มีใครถือ token ที่ตรงกับแถวนั้นอีกเลย
ผู้ดูแลที่เผลอสแกนซ้ำจะได้ `TOKEN_NOT_FOUND` = *"QR นี้ใช้ไม่ได้"* ซึ่ง **โกหก**
(ความจริงคืองานปิดไปแล้ว ไม่ต้องสแกนอะไรอีก)

ปล่อยใบสุดท้ายค้างไว้ → สแกนซ้ำแล้วยังหาแถวเจอ → ตอบ `ALREADY_COMPLETED`
= *"งานนี้ปิดเรียบร้อยแล้ว ไม่ต้องสแกนอีก"* ซึ่งเป็นความจริงและช่วยผู้ใช้ได้จริง

ไม่มีความเสี่ยงเพิ่ม เพราะ session ที่ `CHECKED_OUT` ทำอะไรต่อไม่ได้อยู่แล้ว

### 5.2 ปุ่ม "ออก QR ใหม่" ไม่มีลิมิต

กดรัว ๆ ได้แค่ token ใหม่ไปเรื่อย ๆ ซึ่งไม่ทำให้ใครเสียหาย (เป็นงานของตัวเอง)
ถ้าใส่ลิมิตแล้วผู้ใช้กดพลาดสองที เขาจะเจอ error ที่อธิบายยากทั้งที่ไม่ได้ทำอะไรผิด
→ ยอมให้เขียนดีบีเกินจำเป็นไม่กี่แถว ดีกว่าทำให้คนใช้งานสับสน

### 5.3 กับดักที่ต้องเตือนคนแก้ต่อ

**token ผูกกับ `updated_at` แปลว่าใครก็ตามที่เขียนแถว `job_sessions`
จะทำให้ QR ที่ผู้ใช้ถืออยู่ตายทันที**

โค้ดทุกจุดที่เขียนแถวนี้ตอนนี้เขียน `token_hash` ใหม่ไปพร้อมกันแล้ว (มีเทสคุม)
แต่ถ้ามีใครเพิ่มจุดใหม่แล้วลืม `syncTokenHash()` จะซ่อมให้ตอนอ่านครั้งถัดไป
→ **ระบบไม่พัง** แต่ผู้ใช้จะเห็น QR เปลี่ยนรูปโดยไม่ได้กดอะไร

นี่คือราคาที่จ่ายเพื่อไม่ต้อง migrate — ดูหัวข้อ 6 ถ้าอยากเลิกจ่าย

## 6. ถ้าวันหนึ่งทีมเปิดให้ migrate — สิ่งที่ควรทำ (ยังไม่ต้องทำตอนนี้)

เก็บไว้เป็นข้อเสนอ ไม่ใช่สิ่งที่ค้างอยู่ ระบบตอนนี้ทำงานได้ครบโดยไม่ต้องมีข้อนี้

### 6.1 คอลัมน์ที่จะเพิ่ม

```sql
ALTER TABLE "job_sessions"
    ADD COLUMN IF NOT EXISTS "token_version" INTEGER NOT NULL DEFAULT 0;

ALTER TABLE "job_sessions"
    ADD COLUMN IF NOT EXISTS "token_rotated_at" TIMESTAMPTZ(6);

-- ตัวนับติดลบ = มีบั๊กที่ไหนสักแห่ง ให้ดีบีจับไว้ดีกว่าไปเจอตอนสแกนไม่ผ่าน
DO $$ BEGIN
    ALTER TABLE "job_sessions"
        ADD CONSTRAINT "job_sessions_token_version_check"
        CHECK ("token_version" >= 0);
EXCEPTION WHEN duplicate_object THEN
    RAISE NOTICE 'CHECK job_sessions_token_version_check มีอยู่แล้ว — ข้าม';
END $$;
```

### 6.2 ได้อะไรเพิ่ม

| | |
|---|---|
| `token_version` | เลขรอบที่ **ไม่ผูกกับการเขียนแถว** → กับดักในข้อ 5.3 หายไป |
| `token_rotated_at` | แยก "คนกดปุ่มเมื่อไหร่" ออกจาก "token เปลี่ยนเมื่อไหร่" → หน้าจอบอกผู้ใช้ได้ตรงกว่า |
| — | นับได้ว่า QR ใบนี้ถูกออกใหม่มาแล้วกี่ครั้ง (สัญญาณว่ามีปัญหาการใช้งาน) |

### 6.3 โค้ดที่ต้องแก้ตาม (เล็กมาก)

1. `deriveToken()` — เปลี่ยน `revisionAt.getTime()` เป็น `tokenVersion`
2. `rotateJobQr()` — `{ tokenVersion: { increment: 1 }, tokenRotatedAt: now }`
3. `job-scan.service.ts` — เพิ่ม `tokenVersion: { increment: 1 }` ตอนเช็คอินสำเร็จ
4. entity — เพิ่มฟิลด์ `tokenRotatedAt`

### 6.4 ⚠ ถ้าทำ ต้องรัน backfill ด้วย

การเปลี่ยนสูตรอีกครั้งทำให้ `token_hash` เดิมใช้ไม่ได้อีกรอบ
`syncTokenHash()` จะซ่อมให้ตอนอ่านเหมือนเดิม **จึงยังไม่จำเป็นต้องมีสคริปต์**
แต่ถ้าอยากให้ทุกใบพร้อมใช้ตั้งแต่วินาทีแรกโดยผู้ใช้ไม่ต้องเปิดหน้าก่อน
ให้เขียนสคริปต์ฝั่งแอป (ไม่ใช่ SQL — ต้องใช้ `QR_TOKEN_SECRET`) ไล่ `UPDATE` ทุกแถว
ที่ `status <> 'CHECKED_OUT'`

| `tsc --noEmit` | ไม่มี error ในไฟล์ที่แก้ (เหลือ 1 error เดิมใน `family-group/join-link.service.spec.ts`) |
| `eslint src/monitoring/qr` | 24 error — **ลดลงจาก 28 ที่ค้างอยู่เดิม** |

**เทสที่เพิ่มมาใหม่ คือสัญญาของการ์ดนี้โดยตรง:**

- ★ token ของ `CHECK_IN` กับ `CHECK_OUT` ต้องเป็นคนละค่า — โดยตั้งเลขรอบให้เท่ากันเป๊ะ
  เพื่อพิสูจน์ว่า `action` อยู่ในสูตรจริง ไม่ใช่ผ่านเพราะบังเอิญเวลาต่างกัน
- ★ `rotateJobQr()` เขียน `updated_at` + `token_hash` พร้อมกันด้วย `now` ตัวเดียวกัน
  และ hash ที่ลงดีบีต้องมาจาก token ที่คืนให้ผู้ใช้จริง ๆ
- ★ เช็คอินสำเร็จ → เขียน `token_hash` ของ `CHECK_OUT` ทับในคำสั่งเดียวกัน
  (ถ้าลืมบรรทัดนี้ = ช่องโหว่ที่การ์ดนี้ตั้งใจปิด กลับมาทันที)
- ★ เช็คเอาท์สำเร็จ → **ไม่** เขียน `token_hash` ใหม่ (ข้อ 5.1)
- ★ แถวที่ `token_hash` ล้าสมัยถูกซ่อมให้เองตอนอ่าน — และแถวที่ถูกต้องแล้วต้องไม่เขียนซ้ำ
- ★ patient คนอื่นกด rotate งานของคนอื่นไม่ได้ (ด่านเดียวกับ `jobQr`)

**ยังไม่ได้ทดสอบ:** ยังไม่ได้ยิงกับดีบีจริงแบบ end-to-end
สิ่งที่เทสพิสูจน์คือตรรกะและสูตรถูกต้อง แต่ยังไม่ได้พิสูจน์ว่า `updated_at` ที่วิ่งผ่าน
Postgres `timestamptz(6)` กลับมาเป็นค่ามิลลิวินาทีเดิมเป๊ะ ๆ
โค้ดเขียน `updated_at` เป็น `Date` ของ JavaScript เองทุกจุดเพื่อกันเรื่องนี้ไว้แล้ว
และถึงพลาด `syncTokenHash()` ก็ซ่อมให้ — แต่ควรยืนยันด้วยการทดสอบจริง 1 รอบก่อนขึ้น production
